# 校园食堂线上订餐与错峰取餐系统规划书

## 一、项目背景

校园食堂在集中就餐时段长期存在排队拥挤、菜品信息分散、订单确认效率低等问题。课程项目六要求设计并实现一套线上订餐与错峰取餐系统，把选餐过程前移到线上，把现场处理压缩为取餐码核验。

## 二、总体目标

建设一套可运行、可配置、可打包发布的多角色系统，满足学生、商家和管理员三类用户的核心操作需求，并保证下单、库存、订单状态和权限边界的一致性。

## 三、建设范围

### 第一期范围

- 三类角色的登录与会话管理。
- 食堂窗口、分类、菜品和库存管理。
- 学生在线点餐、购物车、订单和模拟支付。
- 取餐时段预约与取餐码核验。
- 订单取消与库存回补。
- 商家本窗口经营数据查看。
- 管理员统计概览与 CSV 导出。

### 暂不纳入范围

- 真实支付、退款和对账。
- 食堂档口员工排班。
- 移动端原生 App。
- 高并发队列与分布式事务。

## 四、总体方案

系统采用前后端分离架构。后端使用 Spring Boot 暴露 REST 接口，MyBatis 持久化 MySQL 数据，`HttpSession` 维护登录态；前端使用 Vue 3 组织页面，通过统一 API 模块访问后端。构建后的静态资源交给 Spring Boot 托管，因此生产环境只需一个 JAR 和一个端口。

## 五、任务规划

| 阶段 | 主要任务 | 产出 |
| --- | --- | --- |
| 需求梳理 | 明确三类角色与核心流程 | 需求清单 |
| 数据库设计 | 设计用户、窗口、菜品、购物车、订单表 | `schema.sql` |
| 后端骨架 | 建立分层、统一响应和全局异常 | Controller/Service/Mapper 骨架 |
| 认证与会话 | 登录、注销、当前用户、角色限制 | `/api/auth/**` |
| 点餐业务 | 菜品、购物车、拆单、支付、取消 | 订单核心接口 |
| 核验业务 | 取餐码校验、状态推进 | `/api/orders/{id}/verify` |
| 前端实现 | 学生、商家、管理员三类视图 | Vue 页面与样式 |
| 联调优化 | 权限、异常、交互和响应式检查 | 可演示系统 |
| 打包交付 | JAR、文档、数据库脚本和部署说明 | 可交付仓库 |

## 六、里程碑

### M1：基础可用

完成数据库脚本、后端启动、基础数据查询接口，浏览器可以取得窗口和菜品数据。

### M2：核心闭环

学生可以从购物车完成下单、支付和取消；商家可以核验取餐码；管理员可以看到统计数据。

### M3：体验完善

补齐搜索筛选、移动端适配、权限错误提示和页面状态反馈。

### M4：交付打包

完成构建产物、可执行 JAR、文档和演示账号说明，并确认其他同学可复现运行。

## 七、验收指标

- 三个角色均能登录并看到对应功能。
- 学生订单与购物车互不影响。
- 下单扣库存、取消回库存的行为符合预期。
- 任一订单只能由本人、归属商家或管理员操作。
- 商家不能管理其他窗口的菜品或订单。
- 统计页数据能反映订单状态和菜品销量。
- 构建后的 JAR 可独立启动并访问完整网页。

## 八、实施风险与应对

| 风险 | 应对 |
| --- | --- |
| 端口冲突导致启动失败 | 启动前检查 8080，支持 `SERVER_PORT` 覆盖 |
| 数据库结构与代码不同步 | 统一使用 `docs/schema.sql` 初始化 |
| 跨窗口操作造成越权 | 所有写操作按当前会话和归属窗口校验 |
| 并发演示使数据被改乱 | 演示后恢复初始化数据，关键流程用事务保护 |
| 外部 Tomcat 要求与当前 JAR 不一致 | README 保留 WAR 改造步骤，必要时单独打包 |

## 九、交付清单

## 十、后续演进方向

下一阶段可以接入真实支付回调、消息通知、排队叫号、图片上传和更完整的运营报表。如果服务器资源充足，还可以引入 Redis 处理热点库存和会话共享，但课程版本优先保持结构清晰、便于答辩和复现。
